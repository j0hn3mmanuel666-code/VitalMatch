# Preserving existing VitalMatch data

The schema runner is `scripts/migrate-schema.js`. A bare invocation only inspects metadata. The old migration entry points delegate to this runner; none drop, force-sync, rename old profile columns, mark unverified users verified, or replace unknown profile values.

Before applying to a populated database, stop mutation traffic and workers, take a full MySQL dump plus uploaded files, record checksums, and restore the dump to a separate database. If legacy blockchain archives exist, preserve them separately as offline historical files; this version does not read or update them. Compare table counts and inspect representative request, appointment, donor and audit relationships. Retain the verified backup until the upgrade has passed workflow checks. MySQL DDL is not fully transactional; a backup and a staging rehearsal are required.

Set the intended `DB_NAME` explicitly. Run `node scripts/migrate-schema.js` to inspect, then `node scripts/migrate-schema.js --apply --backup-confirmed` only after reviewing the target and backup. Applied versions are recorded in `schema_migrations`; interrupted additive changes can be retried. A failed statement exits nonzero and the version is not marked applied. Existing tables are never rebuilt with force or alter.

The first migration adds verified facility IDs, appointment versions, request quantity/history fields, completed-donation events, recipient-bound confirmation tokens, invitation access, email/outreach outboxes and indexes. It creates `Sessions` before application startup. Unknown historic completion quantities stay null; fulfilled dates are not inferred from `updatedAt`. Legacy scheduled appointments retain their donor/date but require new confirmation. Unbound old schedule links are invalidated. Staff must resend current appointment links. Empty bootstrap or disposable test databases create the same schema without destroying tables.

Migration `20261024_01_system_feedback` adds the `UserFeedbacks` table for signed-in system ratings and administrator review status. It stores the submitting account and role, a 1–5 rating, optional category/comment, and review timestamps. It does not modify existing user or request records.

Hospital names are display snapshots. Historical account/request facility IDs are not guessed by matching names. An administrator must assign each hospital account to a verified Facility, then explicitly link historical records if justified. Existing active requests without facility IDs remain visible to coordinators as unverified; assigning a facility does not certify a medical outcome. The operational donation interval defaults to 56 days via `DONATION_INTERVAL_DAYS` and is a coordination rule, not clinical clearance.

Account removal now deactivates/archives records. Requests and donation event history must be preserved. Do not run hand-written deletion or old bootstrap scripts on production. A reverse code deployment must continue to understand the new tables and statuses; restoring the backup is the recovery option if schema/data acceptance fails. Do not discard newer valid mutations by restoring over an active database.

Use only guarded names beginning `vitalmatch_audit_test_` for disposable integration databases. Test runners must disable email/outreach workers and never use live recipients or providers. Check migration idempotency and lifecycle concurrency on the restored test database before applying to live data.

Donor coordination profiles enforce the existing advertised age range of 18 through 65 using the actual birth date and the Philippine calendar date. Invalid or unknown historic birth dates remain stored for staff review and are excluded from matching; migrations do not invent a birth date or delete an older profile. Completing an already confirmed appointment records what occurred and preserves its history. It does not certify clinical eligibility.

Legacy `hospital_admin` roles are interpreted as the hospital role for access checks, and ordinary administrator account edits normalize that spelling. Neither the schema runner nor this compatibility rule assigns a facility by a typed hospital name. Verified facility membership must be explicitly assigned by an administrator. Historical donation leads retain their old status; new conversion records require an explicitly linked account and conversion date.

Startup checks both the migration ledger and the actual model tables/columns. A current version marker does not bypass a missing security or workflow column. Freeze the reviewed release source when applying each migration. Subsequent schema changes must use a new migration version. Do not edit a recorded version or mark it current manually to bypass a failed schema check.

The known local demo hospital is a synthetic fixture named `VitalMatch Demo Hospital (test data)`. New demo seeding assigns it through the seeded verified demo administrator and records the assignment transactionally. A previously seeded hospital that lacks membership can be inspected with `node scripts/repair-demo-facility.js`; this command prints eligibility booleans only. `node scripts/repair-demo-facility.js --apply` repairs only the exact known seed identities in an explicitly named local nonproduction database, retains existing passwords/profile records, and records an administrator audit entry. Any identity or existing facility mismatch causes refusal. This fixture repair does not infer membership for clinical hospital records.
